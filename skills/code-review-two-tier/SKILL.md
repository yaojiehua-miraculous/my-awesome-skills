# 代码评审：两级结论

评审的价值不在于意见多，而在于"哪些必须改"和"哪些随便"。混在一起说，等于没说。

## 适用 / 不适用

**适用**：有明确 diff 或代码片段，需要给出可否合并的结论。
**不适用**：设计评审（那要看架构文档）；风格纯机械问题（交给格式化工具）。

## 步骤

**Step 1 先看边界，不看实现**
按顺序读：改动文件清单 → 公共接口签名变化 → 数据写入点 → 异常分支。
这一步只回答一个问题：这个改动的影响半径有多大。

**Step 2 分两级**
- **阻断（Blocking）**：会导致数据错误、安全问题、必现故障、破坏兼容、缺少必要测试。必须改完才能合。
- **建议（Nit）**：可读性、命名、重复代码、日志措辞。可以下次改。

判定标准只有一句：**不改会不会出事**。会 → 阻断；只是不够漂亮 → 建议。

**Step 3 只写能落地的意见**
每条意见必须包含：位置 → 现象 → 为什么是问题 → 建议改法。
"这里不太好"不算意见。

**Step 4 给总判**
三选一：`可以合` / `改完阻断项再合` / `不建议合（说明理由）`。不许给"看情况"。

**Step 5 控制篇幅**
阻断项全部列出；建议项最多 3 条，挑最值得改的。剩下不写——写多了等于没重点。

## 检查清单

- [ ] 看过改动文件清单和接口变化，不是只读了一个文件。
- [ ] 每条阻断项都说明了"不改会出什么事"。
- [ ] 建议项 ≤ 3 条，且不是纯风格偏好。
- [ ] 有明确的总判，且与两级结论一致。
- [ ] 没有对没读过的代码发表意见。

## 跑偏信号

1. 十条全是命名和空行。
2. 把"我觉得可以更优雅"写成阻断项。
3. 只评论最容易评论的那一行（通常是缩进）。
4. 总判是"建议再看看"。
5. 对 diff 之外的代码指手画脚。

## 产出

```
总判：可以合 / 改完阻断项再合 / 不建议合
阻断（N 条）：<位置> — <问题> — <不改的后果> — <改法>
建议（≤3 条）：<位置> — <改法>
```
