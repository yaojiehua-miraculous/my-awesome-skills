# 提交信息与提交粒度

一个 commit 应该只回答一件事：为什么改。改了什么，diff 自己会说。

## 适用 / 不适用

**适用**：有未提交改动，需要整理成一次或多次提交。
**不适用**：发布说明、变更日志（那是 changelog 的活）。

## 步骤

**Step 1 读 diff，不读记忆**
`git status` + `git diff --stat` 先看范围；对每个文件确认它属于同一个意图。
发现跨意图（功能 + 格式化 + 依赖升级）→ 拆成多次提交，不要打包。

**Step 2 判断是否该拆**
同一意图的判断标准：把其中一半回滚，另一半是否还成立？成立 → 该拆。

**Step 3 写标题**
格式：`<类型>: <一句话，动宾结构，≤ 50 字>`
类型只用这几个：`feat` / `fix` / `refactor` / `perf` / `test` / `docs` / `chore` / `build`。
标题里写"为什么"，不写"改了哪些文件"。

**Step 4 写正文（可选，但非平凡改动必须有）**
三行以内说清楚：原来的问题 → 这次的取舍 → 有什么副作用或后续。
不写"按需求修改""优化代码"这类空话。

**Step 5 自检**
读一遍标题，问：半年后的我，能不能只看这一行就知道该不该 `git show` 它？

## 检查清单

- [ ] 一次提交只服务一个意图。
- [ ] 标题是动宾结构，含类型前缀，≤ 50 字。
- [ ] 没有把格式化、依赖升级混进功能提交。
- [ ] 非平凡改动有正文说明取舍。
- [ ] 提交前确认没有把 `personal/`、临时文件、密钥带进去。

## 跑偏信号

1. 标题写成"update""修改一下""fix bug"。
2. 一次提交 30 个文件，跨三个意图。
3. 正文抄 diff。
4. `.env`、密钥、本地路径被提交。
5. 用 `git commit -am` 一把梭，没有看过 status。

## 产出

```
<type>: <标题>

<正文三行以内：问题 / 取舍 / 副作用>
```
必要时给出拆分方案：`提交 1：… ｜ 提交 2：…`
