# 接口报错分层定位

一个 500 背后可能有五个不同楼层的问题。先确定楼层，再进房间。

## 适用 / 不适用

**适用**：接口表现异常（状态码、超时、连接失败、返回结构突变），且第一现场信息不完整。
**不适用**：日志里已经明确抛出业务异常（那是业务 bug，直接读代码）；纯前端渲染问题。

## 步骤

**Step 1 固化现象**（先不猜）
抄下四样东西，缺哪样就先要哪样：
- 完整状态码 + 响应体前 200 字符（不要"报错了"三个字）。
- 时间戳与时区（能对上服务端日志的那种）。
- 一次成功与一次失败的请求差异（同一接口、同参数吗？）。
- 调用方是谁：浏览器 / 移动端 / 服务间调用 / 定时任务。

**Step 2 定楼层**（按顺序，命中即停）

| 楼层 | 判据 | 下一步 |
|---|---|---|
| L1 客户端 | 只有某台设备/某个版本报错；请求根本没发出去 | 查跨域、证书、代理、DNS |
| L2 网关 | 5xx 但不是业务链路产生的；响应头带网关标识；502/504 | 查路由规则、上游健康、超时配置 |
| L3 服务 | 服务日志里有对应 trace，且异常在业务代码内 | 读堆栈，定位到具体行 |
| L4 依赖 | 服务日志显示调用下游失败（DB/缓存/第三方） | 查连接数、超时、下游健康 |
| L5 数据 | 服务无异常但结果不对（空、错、重复） | 查入参、事务边界、幂等 |

**Step 3 取证**
只在选定的楼层取证，不要全链路撒网。至少拿到一条能反向证伪的证据（例如"如果把网关超时从 3s 调到 30s 就好"——这就把 L3 排除了）。

**Step 4 给结论**
结论必须包含：楼层、证据、最小修复动作、验证方法。四者缺一件，就不是结论，是猜测。

## 检查清单

- [ ] 有原始状态码和响应体，不是转述。
- [ ] 楼层判断有明确判据，不是"感觉是后端"。
- [ ] 有至少一条反证，排除了相邻楼层。
- [ ] 修复动作是"最小"的（改配置而不是重写模块）。
- [ ] 给了验证方法，且能一分钟内执行。

## 跑偏信号

1. 没要日志就开始猜"可能是数据库"。
2. 直接改业务代码，跳过楼层判断。
3. 把 502 当成应用 500 处理（网关层没看）。
4. 一次给出五种可能，不给取舍。
5. 修复做完却没有验证动作。

## 产出

```
楼层：L?（一句话判据）
证据：<日志原文 / 请求对比>
最小修复：<动作>
验证：<命令或操作>
```
