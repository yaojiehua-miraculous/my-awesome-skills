# 先写一条会失败的测试

没有失败过的测试，等于没有测试。它的唯一价值是"证明我修的问题真的存在，且真的被修好了"。

## 适用 / 不适用

**适用**：修 bug、改公共函数签名、补关键分支（金额、权限、边界、并发）。
**不适用**：纯 UI 样式、一次性脚本、探索性代码（先跑通再补，别本末倒置）。

## 步骤

**Step 1 用一句话写清被测行为**
格式：`给定 <输入/状态>，当 <操作>，则 <可观测结果>`。
写不出来 → 说明你还没想清楚要测什么，回去读代码，不要开始写测试。

**Step 2 挑三个用例，不要更多**
- 正常路径一条（最常见的输入）。
- 边界一条（空、0、最大、超长、并发之一）。
- 出问题的那条（修 bug 时就是复现用例）。

**Step 3 先让测试失败**
跑一次，确认它因**预期的原因**失败（不是语法错、不是 import 错）。
失败的报错要和 Step 1 那句话对得上。

**Step 4 改实现，直到变绿**
只改实现，不改测试断言。如果发现断言本身写错了，回到 Step 1 重写那句话。

**Step 5 补一条防回归的断言**
把这次踩坑的具体现象写进断言消息里，让下次失败的人一眼知道发生了什么。

## 检查清单

- [ ] 每条测试都能对应一句"给定…当…则…"。
- [ ] 至少有一条测试在改代码之前是真失败的（有执行记录）。
- [ ] 用例数在 3–5 条，没有为覆盖率凑数。
- [ ] 断言的是行为，不是实现细节（不 mock 到失去意义）。
- [ ] 断言失败时的消息能自解释。

## 跑偏信号

1. 一次写 20 条测试，全是 happy path。
2. 先改代码再补测试，然后说"测试通过了"。
3. 测试里 mock 掉了被测逻辑本身。
4. 断言写成"不抛异常"就算过。
5. 为了让测试过而放宽断言。

## 产出

```
行为：给定…当…则…
用例：正常 / 边界 / 复现
失败证据：<改代码前的失败输出摘要>
结果：全部通过 + 断言消息可自解释
```
