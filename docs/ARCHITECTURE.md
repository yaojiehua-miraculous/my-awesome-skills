# 架构说明

## 一句话

**用最便宜的索引做路由，用最贵的正文做执行，只在命中时才付这个钱。**

## 三层索引（L0 / L1 / L2）

| 层 | 内容 | 何时读 | 成本上限 |
|---|---|---|---|
| **L0** | 技能名 + 域，一段常驻清单 | 每轮开始 | ≤ 500 token（50 个技能时） |
| **L1** | 单个技能的 `metadata`（priority / type / trigger / scope） | 挑候选时，≤ 3 个 | ≤ 150 token |
| **L2** | 技能正文 | 命中并派活时，≤ 2 份 | ≤ 2 × 1500 token |

L0 放在哪里？**放在 `skills/master-orchestrator/SKILL.md` 末尾的 `MENU` 块里**，
由 `scripts/scan_skills.py --menu` 生成。

这个选择是有原因的：技能正文加载时是**整体**返回的，菜单若单独放一个文件，
模型还得知道它的绝对路径（换机器、换仓库名就失效）。放进指挥人自己的文件里，
"加载指挥人"和"拿到菜单"变成同一个动作，零额外读取、零路径依赖。

## 为什么不是 1000 token

早期设计里写的是"单轮 1000 token 红线"。实测这个数站不住：

- 一份技能正文（中文 1200–1500 字）本身就 ≈ 1200–1500 token。
- 只要命中一次，1000 就必然爆掉。

所以真实红线是 **2000 token / 轮**（L0 500 + L1 150 + L2 一份 1300 左右）。
省 token 的主战场不是 L2（那是价值所在），而是 **L0 和 L1 的膨胀**——
50 个技能若全量读 frontmatter（每个约 60 token），启动就烧 3000 token，
还没干活就用完了预算。这才是要防的事故。

## 三级降级（P0 / P1 / P2）

```
用户请求
  │
  ├─ P0 现成生态 ──── grilling / Superpowers 类；本仓库 skills/ 种子
  │     命中 → 装载 → 执行 → 结束
  │
  ├─ P1 个人资产 ──── personal/ 下自己的技能
  │     命中 → 装载 → 执行 → 结束
  │
  └─ P2 兜底 ──────── 通用能力硬扛
        成功？ ── 是 → skill-forge 归档到 personal/ → 下次变 P1
                 └ 否 → 结束（不归档）
```

复利只发生在最后一条箭头：**P2 成功 → 归档 → 下次变 P1**。
没有这条箭头，这套东西只是一堆静态提示词。

## 为什么路由不用代码

写一个 `router.py` 会立刻带来三个问题：

1. 关键词匹配打不过模型语义——"线上支付好像挂了"没有任何关键词能命中。
2. 个人技能是每天新增的，路由器要跟着改，改到最后没人敢动。
3. 换宿主就要重写。

把路由交给模型，成本是每次读几百 token 的菜单；收益是**新增技能零代码成本**。
在技能数 < 100 的量级上，这笔交易明显划算。超过 100 个再考虑向量检索，但那时更该做的是合并。

## 执行态 vs 资产态

| | 执行态 | 资产态 |
|---|---|---|
| 在哪 | 宿主工具的技能目录（`.dsh/skills`、`~/.claude/skills`） | 本仓库 `skills/` + `personal/` |
| 谁写 | 宿主只读 | 人和 `skill-forge` 写 |
| 形态 | 挂载出来的副本或链接 | 唯一的真身（Markdown + YAML） |

因为资产态是纯文本，所以：换工具带走、跨设备同步、团队共享、版本管理，全都是 Git 的天然能力，
不需要额外做迁移功能。`scripts/mount.py` 只负责把真身"投影"到宿主目录（默认用 junction，
改仓库立刻生效）。

## 宿主兼容性（实测）

DeepSeek Harness 的技能加载规则（从实现里读到的）：

- 技能必须是**顶层** `SKILL.md`：`<root>/<name>/SKILL.md`；**嵌套目录不会被发现**。
  所以 `skills/` 与 `personal/` 必须扁平，不能按 `domain/` 再分一层。
- frontmatter 只认 `name`、`description`、`whenToUse`、`metadata`、`disable-model-invocation`、`user-invocable`。
- 扫描根：`<项目根>/.dsh/skills`（rank 100）、`~/.dsh/skills`（rank 400）等。
- 新增/改名/改 frontmatter 后，**下一个模型步骤**就会重新加载，不需要重启。

这四条直接决定了本仓库的两个设计：所有技能扁平放置；自定义字段全部塞进 `metadata`（宿主官方支持，
不会因为"未知字段"被丢弃）。
