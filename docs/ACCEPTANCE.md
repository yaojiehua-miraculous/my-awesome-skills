# 验收标准

自用验收不看"感觉变聪明了"，只看七个可测的数字。**F1/F2 不过，后面全都别谈。**

## F1 路由准确率（第 1 天就要看）

**定义**：连续 10 次复杂提问中，助手第一步输出【路由】结论的次数占比。
**测量**：拿 10 个真实问题（混合：改代码、查故障、模糊需求各 3 个以上）逐条问，逐条记"有/无"。
**通过线**：≥ 90%（10 次里至少 9 次）。

> 不过线的第一处理不是改提示词，而是检查 `AGENTS.md` 是否被读到、`master-orchestrator` 是否被装载。

## F2 防越界率

**定义**：指挥人**亲自**写业务代码/排查命令，而不是派给对应技能的次数。
**测量**：翻当天对话，看有没有"边调度边干活"。
**通过线**：0 次。这不是比例问题，是纪律问题。

## F3 个人资产积累量

**定义**：`personal/` 下的技能数量。
**通过线**：两周内 3–5 个。少于 3 个说明你没在用（或归档太懒）；多于 10 个说明查重没做。

## F4 查重拦截率

**定义**：试图归档一个"似曾相识"的问题时，被判定为"合并升级"而不是"新建"的比例。
**测量**：每次归档记一行：`新建` 或 `合并`。统计"合并"占比。
**通过线**：≥ 50%（每两个归档里至少一个该合并）。

> 拦截率长期为 0，说明 `skill-forge` 的 Step 4 被跳过了——这是技能库增殖最快的路径。

## F5 轮次压缩比（核心指标）

**定义**：解决**同类**问题所需的对话轮次，改造后 vs 改造前。
**测量**：挑 3 类高频问题，各记录第一次（无技能）与一个月后（有技能）的轮次。
**通过线**：压缩比 ≥ 50%（10 轮 → ≤ 5 轮）。

样本记录：

| 问题类型 | 首次轮次 | 一月后轮次 | 压缩比 |
|---|---|---|---|
| 接口 5xx 定位 | | | |
| 容器起不来 | | | |
| 提交信息整理 | | | |

## F6 采纳率

**定义**：助手给出的方案/代码，你直接采用或只做微调的比例。
**测量**：连续 20 条建议，记 `采用 / 微调 / 重写`。
**通过线**：采用 + 微调 ≥ 80%。（冷启动阶段通常 30% 左右，这就是"复利"的可视化。）

## F7 上下文开销（性能红线）

**定义**：`scan_skills.py` 打印的 L0 菜单 token 数，加上单轮实际装载的 L1/L2 开销。
**通过线**：

| 项 | 红线 |
|---|---|
| L0 菜单（不限技能数） | ≤ 500 token |
| L1 单轮 | ≤ 3 个技能，≤ 150 token |
| L2 单轮 | ≤ 2 份正文 |

**测量**：`python scripts/scan_skills.py --menu` 会打印 L0 估算值和每技能平均值。
超线时的正确动作是**合并技能**，不是删技能，更不是改红线。

## 什么情况下判定为"这套东西对我没用"

诚实一点，以下三条任一成立，就说明方向错了，别硬撑：

1. 七天里一次 P2 归档都没有（说明你的问题重复率太低，不需要技能库）。
2. F5 压缩比始终 < 20%（说明技能写得不可执行，只是换了种形式的笔记）。
3. L0 已经超 500 token 但你还在加技能（说明你在收集，而不是在使用）。
