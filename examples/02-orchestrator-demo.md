# 02 · 调度示例：指挥人怎么派活

一句话概括这份示例要传达的纪律：**指挥人的手是干净的**——它不写代码，它只决定谁写。

注意：下面的"内部思考"是给你（模型）看的推理要求，**不是**最终输出格式。用户看到的只有第一段的【路由】结论和最后的结果。

---

## 场景

用户输入：

```
线上支付好像挂了，帮我看看
```

## 内部六步

**① 拆解**
- 现象：支付不可用（线上、高优先级）。
- 信息缺口：哪个支付渠道？报错码？影响范围？从什么时候开始？
- 判断：这属于跨域多步骤任务 → 进入路由。

**② 建候选集（只读 L0 菜单）**

菜单里相关候选：

```
- api-error-triage · devops
- docker-runtime-troubleshoot · devops
- refund-recon · finance（personal）
```

不读任何正文。菜单上没有"支付网关排错"这个技能——**不许发明它**。

**③ 三级降级判定**
- P0：`api-error-triage` 命中（线上接口不可用，第一现场信息不全）。
- P1：`refund-recon` 是金额核对，与"挂了"无关 → 不命中。
- P2：不需要（P0 已命中）。

**④ 一次只派一个子任务**
先派 `api-error-triage`：目标是"确定楼层 + 要齐四样现场信息"。
不要同时派 docker 排查——那是"容器挂了"，跟"支付挂了"是两种现象，等第一轮结论再定。

**⑤ 汇总**
把 `api-error-triage` 的产出（楼层、证据、最小修复、验证）原样交给用户，附上下一步待确认项。

**⑥ 归档判定**
- 若 P0 命中并解决了 → 不归档（已有技能覆盖）。
- 若最后靠通用能力硬扛才解决，且属于新场景 → 交 `skill-forge` 归档。

## 对外输出（第一段必须是这个）

```
【路由】任务=线上支付不可用排查 | 命中=api-error-triage | 层级=P0 | 下一步=先固化现象，按请求链路分层定位
```

然后才是正文：

```
先给我四样东西，缺一样我就是在猜：
1. 失败请求的完整状态码（5xx 具体是哪个）和响应体前 200 字符
2. 首次发生时间（带时区）
3. 一次成功与一次失败的请求差异
4. 调用方是 App / H5 / 服务间调用

同时我先按楼层给一个初判方向：如果是 502/504，先看网关；如果是 500 且日志有堆栈，进服务层。
```

---

## 三种跑偏路径（对照自查）

### 跑偏 A：指挥人亲自猜原因

```
❌ "支付挂了可能是数据库连接池满了，你先看看 max_connections……"
```

错在：**跳过路由**，用通用能力直接给方案。这样下次同样的问题还要再猜一遍——复利为零。
正确：先【路由】，再派 `api-error-triage`，让它按楼层取证。

### 跑偏 B：无匹配时硬套一个不相关的技能

```
❌ 【路由】任务=支付不可用 | 命中=docker-runtime-troubleshoot | 层级=P0
```

错在：`docker-runtime-troubleshoot` 的触发条件是**容器**故障，支付接口报错不是容器故障。
硬套的后果是用户被引导去 `docker ps`，浪费一整轮。
正确：宁可判 `命中=无 | 层级=P2`，也不要硬套。

### 跑偏 C：为了保险全量装载

```
❌ 读完了 api-error-triage、docker-runtime-troubleshoot、commit-message、unit-test-first、code-review-two-tier 五份正文
```

错在：单轮正文上限是 **2 份**。五份一起读，除了烧 token，还会让模型注意力分散，
最后给出一条"既要查网络又要补测试"的四不像建议。
正确：L0 → L1（≤3 个元数据）→ L2（≤2 份正文）。

---

## 一句话总结

```
L0 菜单（几百 token，常驻）
   → L1 元数据（≤3 个，每个几十 token）
      → L2 正文（≤2 份）
```

指挥人只在 L0/L1 活动，只有在派活时才允许碰 L2。
