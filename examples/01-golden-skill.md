# 退款与结算金额差异核对

先算清楚，再解释。差异一定有来源，找不到来源就是还没拆到位。

## 适用 / 不适用

**适用**：单笔或批量退款金额与应收/应付/对账文件不一致；用户反馈"多退了""少退了"。
**不适用**：退款流程根本没走通（那先查支付渠道返回码）；汇兑损益类差异（另属财务口径）。

## 步骤

**Step 1 固化三个数**
- 订单原始金额（含税、含运费）
- 实际退款金额
- 期望退款金额（用户或财务口径）

三者齐了才开工。缺"期望值"就别猜，先问清楚口径。

**Step 2 四段拆解**
```
期望 = 数量 × 单价 − 优惠分摊 − 已退金额
```
逐段代入实际值，找出第一个对不上的段。**只查这一段**，不要四段一起怀疑。

**Step 3 常见成因对照**

| 差异特征 | 首要怀疑 |
|---|---|
| 差额正好等于运费 | 运费是否参与退款 |
| 差额是单价的整数倍 | 部分退款时数量口径 |
| 差额是小数、带分位误差 | 优惠分摊的取整方式 |
| 差额等于上一笔退款额 | 重复退款 / 幂等失效 |
| 差额比例固定（如 99%） | 渠道手续费扣减 |

**Step 4 取证**
拉一次该订单的退款流水（时间、金额、渠道返回码），确认是否真的发生了两次扣减。
流水只有一条但金额错 → 计算逻辑问题；流水有两条 → 幂等问题。这两类修复方式完全不同。

**Step 5 给结论**
写明：差异段、成因、影响范围（单笔 / 同批次 / 全部）、修复动作、是否需要补退或追回。

## 检查清单

- [ ] 三个数都固化了，口径一致（含税/不含税先说清）。
- [ ] 用四段公式定位到唯一一段，没有同时怀疑四段。
- [ ] 拉了流水，区分了"算错"和"退两次"。
- [ ] 给了影响范围，不只是修这一笔。
- [ ] 需要补退/追回时，给出了执行人和验证方式。

## 跑偏信号

1. 没算就解释"可能是优惠券的问题"。
2. 把取整误差当成 bug 修（先确认业务上允许多少分位误差）。
3. 只修当前这一笔，不评估同批次。
4. 用"重新退一次"来验证（会制造二次差异）。
5. 结论里没有影响范围。

## 产出

```
差异段：数量 / 单价 / 优惠 / 已退
成因：<一句话>
影响范围：<单笔 / 批次号 / 全部>
修复：<动作 + 是否需要补退>
验证：<重算后的三个数>
```

## 这张表说明什么叫"不合格"

| 不合格写法 | 错在哪 | 改成 |
|---|---|---|
| `description: 支付领域全能助手` | 没有触发条件，永远不会被命中，或在任何场景被误命中 | 写"当……时触发"，且只覆盖一个场景 |
| 正文写三段"背景与意义" | 技能是用来执行的，不是用来阅读的 | 换成可执行步骤，每步有可验证的中间结果 |
| `scope: global` | 财务口径是私有资产，公开即泄漏业务逻辑 | `scope: personal` |
| 没有「跑偏信号」段 | AI 不知道边界在哪，会过度发挥 | 列出 3–6 条它最可能犯的错 |
| `trigger: 支付` | 一个词太宽，会把所有支付问题都吸过来 | 写用户真实会说的症状词 |
| 正文里出现真实客户名/域名 | 泄漏 | `<CUSTOMER>` `<HOST>` 占位符 |

## 自检口诀

- **description 读一遍**：能不能判断"该不该命中"？
- **正文读一遍**：能不能照着做？
- **跑偏信号读一遍**：知不知道边界在哪？

三个都能 → 及格。缺一个 → 回去改。
